Context 记录副作用的所有权

插件卸载的难点不是调用清理函数，而是知道哪些清理函数属于这个插件。

先看泄漏

function apply() {
  bus.on("message", listener)
  setInterval(refresh, 1000)
}

apply()
// 如何完整卸载？

监听器和定时器都创建成功了，但调用方没有拿到它们的所有权信息。丢失的不是清理能力，而是“谁应当负责清理”的关系。

Cordis 的工作模型

Plugin只通过自己的 ctx 注册
Context把 effect 交给当前 Fiber
Fiber卸载时执行全部 disposer
const plugin = root.plugin((ctx) => {
  ctx.effect(() => {
    bus.on("message", listener)
    return () => bus.off("message", listener)
  })
})

plugin.dispose()

Mini 版使用一个 Context 类：实例保存自己的 active 状态和 disposer 列表，对外只提供 effect、plugin 和 dispose。

Context 不是自动发现副作用的垃圾回收器。只有通过 ctx.effect() 或基于它实现的 API 注册的资源，才会归属于插件生命周期。

树从哪里来

const root = new Context()

root.plugin((pluginA) => {
  pluginA.plugin((pluginB) => {
    pluginB.effect(() => () => offBTimer())
  })
})

每次 plugin() 都先创建 child，再把 child.dispose() 登记为父 Context 的 effect。父作用域持有子作用域的 disposer，这一条边就是插件树；不需要 children 数组或 parent 字段。

检索练习

为什么只让插件返回一个 disposer 仍然不够？

嵌套 helper 和子插件必须层层合并、传递 disposer；任何一层遗漏，卸载就不完整。

Context 与 Fiber 各自负责什么？

Context 是插件使用的作用域入口；Fiber 保存该作用域的状态和 disposer，并真正执行卸载。

直接调用 setInterval 会被自动清理吗？

不会。必须把 clearInterval 注册为 effect，或使用内部已经调用 effect 的 Cordis API。

动手验证

打开测试文件，先不要运行代码，尝试预测“父插件、子插件、父插件最后注册的 effect”会以什么顺序清理。然后执行： 

node --test examples/mini-cordis/context.test.ts

如果预测顺序与测试结果不同，回到“子 Context 自己也是父 Context 的一个 effect”这条关系，再画一次注册顺序和卸载顺序。
